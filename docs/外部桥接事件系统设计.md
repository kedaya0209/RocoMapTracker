# 外部桥接事件系统设计

## 1. 背景与目标

rmt_bridge.py 最初仅用于嗅探 `0x0133` 包中的 `scene_cfg_id`，控制 SIFT 匹配的启停。随着需求扩展，外部桥接将发展为**游戏事件总线路由器**，统一接收并分发多种游戏事件。

### 核心目标

- **单一职责**：rmt_bridge.py 负责嗅探 + 协议转换，不做业务逻辑
- **事件驱动**：Java 侧以路由器模式分发事件，各模块按需订阅
- **可扩展**：新增事件类型只需加协议常量 + 注册处理器，不改现有逻辑
- **协议分离**：外部桥接协议与 SIFT 内部协议完全解耦

## 2. 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    游戏进程 (Roco Kingdom)                     │
│                        TCP :8195                             │
└──────────────────────────┬──────────────────────────────────┘
                           │ 加密流量
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                 rmt_bridge.py (Python)                        │
│                                                              │
│  AsyncSniffer ─→ 解密 0x4013 ─→ opcode 路由                  │
│       │               │              │                       │
│  0x0133场景      0x0414区域     0x0243拾取                    │
│       │               │              │                       │
│  ─────┴───────────────┴──────────────┴── → SocketServer      │
└─────────────────────────────────────────────────────────────┘
                           │ TCP (loopback)
                           ▼
┌─────────────────────────────────────────────────────────────┐
│           RocoMapTracker (Java / roco-engine)                │
│                                                              │
│  SocketServer                                                │
│       │                                                     │
│  ExternalBridgeHandler (路由器)                               │
│    │           │              │                              │
│    ▼           ▼              ▼                              │
│ 场景控制    区域追踪      物资拾取        ← 后续: 战斗事件    │
│    │           │              │                              │
│    ▼           ▼              ▼                              │
│ SiftConfig  [预留]   MaterialCollectionContext                │
│                    [日志/显示]                                │
└─────────────────────────────────────────────────────────────┘
```

### 数据流

```
游戏服务器 → TCP 加密包 → bridge 解包 → 按 opcode 分流
  → 封装为 MSG_* 二进制消息 → SocketServer
  → ExternalBridgeHandler 路由 → 具体业务模块
```

## 3. 协议层

### 3.1 ExternalBridgeProtocol（Java 常量类）

```java
// roco-engine/.../socket/ExternalBridgeProtocol.java
public final class ExternalBridgeProtocol {
    // 210-219: 外部桥接协议段（与 SIFT 内部协议 200-209 隔离）
    public static final int MSG_EXTERNAL_POSITION = 210; // 废弃
    public static final int MSG_SCENE_CHANGE     = 211;
    public static final int MSG_STOP_MATCHING    = 212;
    public static final int MSG_START_MATCHING   = 213;
    public static final int MSG_AREA_CHANGE      = 214;
    public static final int MSG_ITEM_PICKUP       = 215;
    // 预留 216-219 给后续事件（战斗、任务等）
}
```

### 3.2 消息帧格式

```
[4B serviceId][4B bodyLength][NB body]
```
- Big-Endian 编码
- `body` 为空时仅发 8 字节头部（如 MSG_STOP_MATCHING）
- 具体 body 编码见各事件定义

### 3.3 协议常量对照表

| 常量 | 值 | 方向 | Body | 触发条件 | 对应 opcode |
|------|-----|------|------|---------|------------|
| MSG_HELLO | 1 | C→S | clientId | 连接建立 | — |
| MSG_SCENE_CHANGE | 211 | C→S | `uint32 scene_cfg_id` | 场景切换 | 0x0133 |
| MSG_STOP_MATCHING | 212 | C→S | 空 | 离开主世界 | 0x0133 |
| MSG_START_MATCHING | 213 | C→S | 空 | 进入主世界 | 0x0133 |
| MSG_AREA_CHANGE | 214 | C→S | `uint32 area_func_conf_id` | 进入新区 | 0x0414 |
| MSG_ITEM_PICKUP | 215 | C→S | `uint32 goods_id` | 拾取物品 | 0x0243 |

## 4. 事件分发 (ExternalBridgeHandler)

### 4.1 当前架构

ExternalBridgeHandler 实现 `HandlerSubscriber.MessageHandler` 接口，作为单一路由器：

```java
@ThreadSafe
@Slf4j
public class ExternalBridgeHandler implements HandlerSubscriber.MessageHandler {
    // 场景控制
    private final Runnable onStopEngine;
    private final Runnable onStartEngine;

    @Override
    public void onMessage(int serviceId, byte[] body, SocketSession sender) {
        switch (serviceId) {
            case ExternalBridgeProtocol.MSG_STOP_MATCHING  → onStopEngine
            case ExternalBridgeProtocol.MSG_START_MATCHING → onStartEngine
            // MSG_SCENE_CHANGE / MSG_AREA_CHANGE / MSG_ITEM_PICKUP → 待接入
        }
    }
}
```

### 4.2 后续演进方向

当事件类型增多后，可考虑将路由器拆分为**多订阅模式**：

```
ExternalBridgeHandler 作为轻量路由器
  ├─ MSG_STOP/START_MATCHING → 直接回调（已有）
  ├─ MSG_SCENE_CHANGE       → 广播到场景监听器
  ├─ MSG_AREA_CHANGE        → 广播到区域监听器
  ├─ MSG_ITEM_PICKUP        → 广播到物资监听器
  └─ MSG_BATTLE_*           → 广播到战斗记录器 (预留)
```

有两种实现方案：

**方案 A：ExternalBridgeHandler 继续膨胀**
- 优点：改动最小
- 缺点：serviceId 分支会越来越多

**方案 B：借鉴 SocketServer 注册中心模式，让业务模块直接注册**
```java
SocketServer.instance().registerExternal(
    ExternalBridgeProtocol.MSG_ITEM_PICKUP,
    itemPickupHandler);
```
- 优点：ExternalBridgeHandler 消失，零耦合
- 缺点：需要 SocketServer 支持"外部消息"注册

**当前推荐**：先用方案 A，等战斗事件接入时再评估是否切到方案 B。

## 5. 场景控制事件

### 5.1 触发条件

bridge 嗅探到 `0x0133` (ZONE_SCENE_MOVE_REQ) 包，提取 `scene_cfg_id`。

### 5.2 业务逻辑

```
scene_cfg_id = 103 (卡洛西亚大陆)  → MSG_START_MATCHING → 启动 SIFT 匹配
scene_cfg_id ≠ 103                → MSG_STOP_MATCHING  → 停止 SIFT 匹配
```

### 5.3 关键代码

```python
# rmt_bridge.py
sid = int(scene_cfg_id)
if sid == self._main_world_scene_id:  # 103
    self.rmt_sender.send_start_matching()
else:
    self.rmt_sender.send_stop_matching()
```

```java
// ModernCanvasApp.java — 注册
ExternalBridgeHandler bridgeHandler = new ExternalBridgeHandler(
    () -> SiftConfig.SIFT_MATCHING_ENABLED = false,
    () -> SiftConfig.SIFT_MATCHING_ENABLED = true);
SocketServer.instance().registerInternal(
    ExternalBridgeProtocol.MSG_STOP_MATCHING, ...);
SocketServer.instance().registerInternal(
    ExternalBridgeProtocol.MSG_START_MATCHING, ...);
```

## 6. 区域追踪事件

### 6.1 触发条件

bridge 嗅探到 `0x0414` (ZONE_SCENE_PLAY_ACTS_NOTIFY) 包，遍历 `acts` 数组中的 `enterted_catcher` 动作，提取 `area_func_conf_id`。

### 6.2 数据来源

| 层级 | 配置 | 关键字段 |
|------|------|---------|
| AREA_FUNC_CONF.json | 区域功能配置 | `area_func_id` → `area_id`, `name_priority`, `broadcast_type` |
| AREA_CONF.json | 区域几何定义 | `area_id` → `name`, `polygon_points` |
| LAYERED_WORLD_MAP_CONF.json | 分层地图 | `area_func_id` → `map_layer_group`, `camp_id` |

### 6.3 消息体

```
[4B area_func_conf_id]  // uint32, big-endian
```

### 6.4 未完成项

- Java 侧 MSG_AREA_CHANGE 尚未注册处理器
- 需要加载 AREA_FUNC_CONF.json 做 ID→名称的查找
- 后续可集成到 UI 显示当前区域名

## 7. 物资拾取事件

### 7.1 触发条件

bridge 嗅探到 `0x0243` (ZONE_GOODS_REWARD_NOTIFY) 包，提取 `goods_id` 和 `flow_reason`。

### 7.2 FlowReason 过滤策略

ProtoEnum.FlowReason 中相关值：

| 值 | 常量名 | 说明 | 是否场景拾取 |
|----|--------|------|------------|
| 0 | NORMAL | 常规拾取 | ✅ |
| 2 | RT_DROP | 击杀掉落 | ✅ |
| 85 | COLLECT | 场景采集 | ✅ |
| 126 | SCENE_MAGIC_OBJECT_AWARD | 场景交互 | ✅ |
| 141 | ACTIVITY_DROP | 活动掉落 | ✅ |
| 3 | TASK_REWARD | 任务奖励 | ❌ |
| 5 | MALL_BUY | 商城购买 | ❌ |
| 7 | BAG_SELL | 背包出售 | ❌ |

**实现策略**：初始阶段不过滤，全部上报。观察一段时间后，在 bridge 侧加白名单。

### 7.3 消息体

```
[4B goods_id]  // uint32, big-endian
```

### 7.4 与现有 OCR 系统的关系

```
OCR 系统 (OcrProcessor)
  └→ ROI-1 截取物品栏 → 模板匹配 → 计数更新 → MaterialCollectionContext

网络拾取 (MSG_ITEM_PICKUP)
  └→ 实时推送 goods_id → MaterialCollectionContext.updateFromNetwork()
      └→ 增量累加（做不了精确绝对值的 OCR 的补充）
```

两者共存模式：
- **OCR**：负责定时扫描物品栏，维护精确的绝对值计数
- **网络拾取**：负责实时通知"拾取了什么"，可触发 UI 反馈（Toast、计数动画）
- 网络拾取也可作为 OCR 的"增量"输入，减少 OCR 扫描频率

### 7.5 MaterialCollectionContext 扩展

```java
public class MaterialCollectionContext {
    // 现有 OCR 入口
    public void updateFromOcr(Map<Integer, Integer> itemCounts);

    // 新增网络入口
    public void updateFromNetwork(int goodsId);
    public void updateFromNetwork(int goodsId, int quantity);
}
```

## 8. 战斗事件（预留）

### 8.1 设计目标

战斗事件需要在外部桥接系统中预留扩展点，待功能开发时接入：

- 战斗开始/结束通知
- 己方/对方队伍宠物序列
- 每回合行动记录
- 自动暂停 SIFT 匹配

### 8.2 预留协议段

```
MSG_BATTLE_START  = 216  // 战斗开始
MSG_BATTLE_END    = 217  // 战斗结束
MSG_BATTLE_TURN   = 218  // 回合记录
// 预留 216-219
```

### 8.3 架构准备

战斗事件需要承载结构化数据（队伍信息、回合记录），建议使用 JSON 编码而非定长二进制：

```
[4B serviceId][4B bodyLength][NB JSON body]
```

Java 侧用 Jackson/Gson 反序列化为 POJO。
